# Обзор архитектуры системы

Данный документ описывает архитектуру платформы SPEC CRM/ERP с использованием подхода [модели C4](https://c4model.com/) — от контекста системы до ключевых взаимодействий между контейнерами.

## 1. Контекст системы

Платформа SPEC CRM/ERP предназначена для сотрудников компаний сферы HVAC (менеджеры, инженеры, кладовщики, бухгалтеры) и интегрируется с внешними системами.

**Акторы:**

| Актор                 | Описание                                                          |
|-----------------------|-------------------------------------------------------------------|
| Менеджер HVAC         | Создаёт сделки, назначает задачи, отслеживает тендеры             |
| Выездной инженер      | Выполняет задачи, ведёт учёт времени, заполняет чек-листы         |
| Кладовщик             | Управляет запасами, обрабатывает заявки на материалы              |
| Бухгалтер             | Просматривает отчёты по зарплатам, амортизацию, финансовую аналитику |
| AI-агент              | Автоматизирует операции через MCP (создание задач, проверка остатков) |

**Внешние системы:**

| Система       | Точка интеграции                | Назначение                                      |
|---------------|--------------------------------|-------------------------------------------------|
| Keycloak      | OIDC / JWT                     | Аутентификация и SSO, управление ролями         |
| MinIO         | S3 API                         | Хранение документов и фотографий                |
| Telegram      | Bot API (через Celery worker)  | Push-уведомления выездным инженерам             |
| zakupki.gov   | Ручной ввод / будущий парсер   | Источник тендеров                               |

## 2. Диаграмма контейнеров

| Контейнер        | Технология             | Порт  | Зона ответственности                                                  |
|------------------|------------------------|-------|-----------------------------------------------------------------------|
| **Фронтенд**    | Next.js 15 (React)     | 3000  | SSR-интерфейс, Kanban-доски, формы, дашборды                         |
| **Backend API**  | FastAPI + Uvicorn      | 8000  | REST API, WebSocket для реального времени, валидация JWT              |
| **MCP-сервер**   | FastMCP (Python)       | 8001  | MCP-сервер для интеграции с AI-агентами                              |
| **Celery Worker**| Celery 5.4 (Python)    | —     | Асинхронные задачи: уведомления, мониторинг SLA, амортизация, отчёты |
| **Celery Beat**  | Celery Beat            | —     | Планировщик периодических задач (проверки SLA, расчёт амортизации)    |
| **PostgreSQL**   | PostgreSQL 16          | 5432  | Основное хранилище данных для всех сущностей                         |
| **Redis**        | Redis 7                | 6379  | Слой кеширования, брокер Celery (db 1), результаты Celery (db 2)    |
| **MinIO**        | MinIO (S3-совместимый) | 9000  | Объектное хранилище для документов, фотографий, подписанных актов    |
| **Keycloak**     | Keycloak 25.0          | 8080  | OIDC-провайдер идентификации, управление пользователями, RBAC        |
| **Nginx**        | Nginx (alpine)         | 80    | Обратный прокси, раздача статики, SSL-терминация (прод)              |


## 3. Ключевые архитектурные решения

### Почему собственный движок задач, а не Plane/Taiga

Готовые инструменты управления проектами не обладают семантикой рабочих процессов, специфичной для HVAC: шлюзовые чек-листы, блокирующие смену статуса; автоматическое списание материалов со склада при завершении задачи; контроль SLA с отраслевыми дедлайнами; создание задач по шаблонам с настраиваемыми пользовательскими полями. Собственный движок обеспечивает полный контроль над конечным автоматом и авто-действиями, избавляя от накладных расходов на адаптацию универсального инструмента.

См. [ADR-001](../adr/001-custom-task-engine.md) для полного описания решения.

### Почему чистый PostgreSQL (без Document DB)

Все сущности имеют чётко определённую реляционную структуру с жёсткими требованиями к ссылочной целостности (задачи → шаблоны → чек-листы, складские движения → позиции → задачи). JSONB-колонки обеспечивают гибкость документного хранилища там, где это нужно (определения воркфлоу, пользовательские поля, конфигурации зарплат), не жертвуя транзакционными гарантиями и производительностью запросов. Нативная JSONB-индексация PostgreSQL (GIN) эффективно обрабатывает как структурированные, так и полуструктурированные запросы.

### MCP-first интеграция с AI

Вместо создания собственного API чат-бота платформа реализует стандарт Model Context Protocol. Это позволяет любому MCP-совместимому AI-клиенту (Cursor, Claude Desktop, пользовательские агенты) подключиться мгновенно без специального интеграционного кода. MCP-сервер использует ту же кодовую базу, модели и бизнес-логику, что и REST API, обеспечивая согласованность.

## 4. Обоснование выбора технологий

| Решение                    | Выбор                   | Обоснование                                                                     |
|----------------------------|-------------------------|---------------------------------------------------------------------------------|
| Фреймворк API              | FastAPI                 | Нативный async, автогенерация OpenAPI, интеграция с Pydantic, зрелая экосистема |
| ORM                        | SQLAlchemy 2 (async)    | Отраслевой стандарт, полная async-поддержка, гибкое построение запросов          |
| Аутентификация             | Keycloak OIDC           | Корпоративный SSO, RBAC, федерация пользователей, не нужно писать код авторизации |
| Библиотека MCP             | FastMCP 3.1+            | Официальный Python SDK, streamable HTTP транспорт, инструменты на декораторах   |
| Очередь задач              | Celery + Redis          | Проверенное решение, поддержка периодических задач (Beat), горизонтальное масштабирование |
| Объектное хранилище        | MinIO                   | S3-совместимый, self-hosted, прямая замена AWS S3 в проде                       |
| Фронтенд                   | Next.js 15              | SSR, App Router, TypeScript-first, обширная экосистема компонентов              |
| Сериализация               | orjson                  | В 3–10 раз быстрее стандартной JSON-сериализации, используется как default в FastAPI |
| Логирование                | structlog               | Структурированное JSON-логирование, привязка контекста, удобный консольный вывод |
| База данных                | PostgreSQL 16           | JSONB, GIN-индексы, CTE, оконные функции, надёжность                           |
| Валидация                  | Pydantic v2             | Rust-ядро для производительности, бесшовная интеграция с FastAPI/SQLAlchemy     |

## 5. Диаграммы потоков данных

### 5.1 Создание задачи из шаблона

```
AI-агент / Пользователь
      │
      ▼
  [create_task / POST /api/v1/tasks]
      │
      ├─ 1. Получить TaskTemplate по template_id
      │     └─ Загрузить workflow_definition, чек-листы, поля, конфигурацию SLA
      │
      ├─ 2. Определить initial_state из workflow_definition
      │
      ├─ 3. INSERT строки Task
      │     └─ status = initial_state, custom_fields = входные значения
      │
      ├─ 4. Копировать TemplateChecklists → строки Checklist + ChecklistItem
      │
      ├─ 5. Рассчитать sla_deadline из sla_config.max_duration_hours
      │
      ├─ 6. INSERT TaskStatusHistory (начальная запись)
      │
      └─ 7. Вернуть созданную задачу с чек-листами
```

### 5.2 Переход по воркфлоу

```
Пользователь / AI-агент
      │
      ▼
  [transition_task / POST /api/v1/tasks/{id}/transition]
      │
      ├─ 1. Загрузить Task + Template.workflow_definition
      │
      ├─ 2. Найти подходящий переход (from_status → to_status)
      │     └─ Если не найден → 409 WORKFLOW_TRANSITION_DENIED
      │
      ├─ 3. Проверить условия:
      │     ├─ Обязательные роли  → user.roles ∩ transition.required_roles
      │     ├─ Обязательные поля  → task.custom_fields[key] не пусты
      │     ├─ Шлюзовые чек-листы → checklist.is_completed == true
      │     └─ Обязательные документы → COUNT(documents) по типу >= min_count
      │
      ├─ 4. Обновить task.status, установить started_at / completed_at
      │
      ├─ 5. INSERT TaskStatusHistory
      │
      ├─ 6. Выполнить auto_actions:
      │     ├─ deduct_warehouse  → UPDATE warehouse_items, INSERT movement
      │     ├─ complete_time_entry → закрыть открытые записи TimeEntry
      │     └─ notify            → INSERT Notification + отправка через Celery
      │
      └─ 7. Вернуть обновлённую задачу
```

### 5.3 Загрузка файла

```
Пользователь (Фронтенд / Мобильное приложение)
      │
      ▼
  [POST /api/v1/documents/upload]
      │
      ├─ 1. Валидация файла (размер, MIME-тип)
      │
      ├─ 2. Генерация ключа хранения:  {task_id}/{uuid}/{filename}
      │
      ├─ 3. Загрузка в бакет MinIO (hvac-documents)
      │     └─ Multipart upload через boto3 / presigned URL
      │
      ├─ 4. INSERT строки Document
      │     └─ storage_path, mime_type, file_size, doc_type, label
      │
      ├─ 5. INSERT DocumentVersion (version = 1)
      │
      └─ 6. Вернуть метаданные документа с URL для скачивания
```
