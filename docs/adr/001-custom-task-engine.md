# ADR-001: Собственный движок задач вместо интеграции Plane/Taiga

**Дата:** 2026-03-01
**Статус:** Принято
**Принято:** Архитектурная команда

## Контекст

Платформе SPEC CRM/ERP требуется система управления задачами со следующими отраслевыми требованиями:

1. **Создание задач по шаблонам** — переиспользуемые чертежи для воркфлоу монтажа, обслуживания, ремонта и инспекции с настраиваемыми пользовательскими полями, чек-листами и параметрами SLA.
2. **Движок воркфлоу со шлюзовыми условиями** — конечный автомат, в котором переходы между статусами защищены проверками ролей, завершения чек-листов, загрузки обязательных документов и валидации обязательных полей.
3. **Авто-действия при переходах** — автоматическое списание складских запасов, закрытие записей учёта времени и многоканальные уведомления, срабатывающие при определённых сменах статуса.
4. **Глубокая интеграция со складом, учётом времени и зарплатным модулем** — завершение задачи напрямую влияет на складские остатки, учёт рабочих часов и расчёт заработной платы.
5. **MCP-first интеграция с AI** — все операции с задачами должны быть доступны как инструменты Model Context Protocol для автоматизации AI-агентами, с той же бизнес-логикой, что и REST API.

Мы оценили три варианта:

### Вариант A: Интеграция Plane (open-source)

[Plane](https://plane.so/) предоставляет Kanban-доски, задачи и модули. Однако:
- Нет концепции шаблонов задач с настраиваемыми пользовательскими полями
- Нет движка воркфлоу со шлюзовыми условиями или авто-действиями
- Нет встроенной интеграции со складом/инвентарём
- Потребовался бы значительный форк/расширение для поддержки HVAC-специфичных воркфлоу
- Отдельная база данных и API-поверхность — дублирование авторизации, сложность синхронизации данных
- Интеграция с MCP потребовала бы промежуточного слоя

### Вариант B: Интеграция Taiga (open-source)

[Taiga](https://taiga.io/) предлагает Scrum/Kanban с пользовательскими полями и воркфлоу. Однако:
- Настройка воркфлоу ограничена порядком статусов, без условных переходов
- Нет шлюзовых чек-листов (чек-листы есть, но не блокируют переходы)
- Нет системы авто-действий для складских списаний или уведомлений
- Построен на Django — отличный технологический стек от нашего бэкенда на FastAPI
- Потребовалось бы поддерживать отдельный сервис с собственной базой PostgreSQL

### Вариант C: Собственная разработка (выбран)

Создать собственный движок задач в рамках существующей кодовой базы FastAPI/SQLAlchemy:
- Класс `WorkflowEngine`, реализующий валидацию КА и авто-действия
- Модель `TaskTemplate` с JSONB-полем `workflow_definition`
- Общая база данных, общая бизнес-логика, общая аутентификация (Keycloak JWT)
- Нативное предоставление MCP-инструментов из того же процесса Python

## Решение

**Создать собственный движок задач** в рамках существующей кодовой базы бэкенда.

Движок задач реализован как:
- ORM-модель `TaskTemplate` с `workflow_definition` (JSONB КА), дочерними моделями `TemplateChecklist`, `TemplateField` и `TemplateStage`
- Сервисный класс `WorkflowEngine` (`backend/app/services/workflow_engine.py`) с методами: `validate_transition`, `execute_transition`, `get_available_transitions`
- Валидаторы шлюзовых условий: `_check_required_roles`, `_check_required_fields`, `_check_required_checklists`, `_check_required_documents`
- Исполнители авто-действий: `_action_deduct_warehouse`, `_action_complete_time_entry`, `_action_notify`
- MCP-инструменты (`task_tools.py`, `template_tools.py`), вызывающие тот же сервисный слой
- REST API эндпоинты (`/api/v1/tasks/`, `/api/v1/templates/`), вызывающие тот же сервисный слой

## Последствия

### Положительные

- **Полный контроль над семантикой воркфлоу** — шлюзовые условия, авто-действия и движок КА реализованы именно так, как требует HVAC-домен, без обходных решений или ограничений внешних зависимостей.
- **Единая база данных** — задачи, шаблоны, склад, записи времени и данные по зарплатам находятся в одном экземпляре PostgreSQL с гарантиями ссылочной целостности и транзакционности.
- **Единая авторизация** — валидация JWT Keycloak в одном месте; не нужно синхронизировать пользовательские сессии между сервисами.
- **Нативная MCP-интеграция** — MCP-инструменты вызывают тот же Python-сервисный слой, что и REST-эндпоинты, обеспечивая консистентность бизнес-логики без промежуточного адаптера.
- **Производительность** — никаких межсервисных сетевых вызовов для операций с задачами; все запросы — прямой SQL через SQLAlchemy.
- **Простота деплоя** — один контейнер бэкенда обслуживает и REST, и MCP; нет дополнительного сервиса для развёртывания, мониторинга или обновления.

### Отрицательные

- **Больше начальных усилий на разработку** — создание движка воркфлоу, системы шаблонов и Kanban UI с нуля требует больше инженерных ресурсов, чем интеграция существующего инструмента.
- **Бремя поддержки** — мы владеем всей кодовой базой управления задачами, включая граничные случаи (конкурентные переходы, гонки состояний чек-листов, версионирование шаблонов).
- **Нет готового UI от сообщества** — у Plane/Taiga отшлифованные, проверенные в бою фронтенды; нам необходимо создать собственную Kanban-доску, страницы задач и редакторы шаблонов на Next.js.

### Меры по снижению рисков

- Движок воркфлоу хорошо изолирован в `WorkflowEngine` с комплексными методами валидации, что делает его тестируемым и поддерживаемым.
- Шаблонный подход означает, что добавление новых типов воркфлоу (напр. «Монтаж VRF-системы», «Чистка воздуховодов») требует только создания нового шаблона в базе данных — без изменений кода.
- Фронтенд Kanban-доски использует проверенные React-библиотеки (dnd-kit) и взаимодействует с бэкендом через стандартные REST-эндпоинты.
